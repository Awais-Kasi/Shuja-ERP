01

Stack & justification

Every choice below leans on two things you already told me and one thing your machine told me: you want maintainable and performant, the accounting must be strictly consistent, and your box is a fully-loaded Laragon install (PHP 8.4, Composer, Redis, Node 22, Yarn). That makes a Laravel monolith the path of least resistance and the most robust choice — one deployable unit, one transaction boundary around the ledger, no network hop between a module and the posting engine.

One deliberate trade-off

A monolith over microservices. For an ERP, the accounting invariant — every business event lands as a balanced journal, atomically — is far easier to guarantee inside one database transaction than across services. We keep clean module boundaries in code (a Domain\ layer per module) so it stays maintainable, without paying the distributed-systems tax on consistency.

02

System architecture

Requests flow through a thin HTTP layer into module domain services, which never touch the ledger directly — they hand a business event to the Posting Engine, the single component allowed to write journals. Reads for heavy screens come off cached, pre-aggregated balances; writes go through Postgres transactions.

04

Foundation & multi-tenancy

Every business table carries a company_id. A global Eloquent scope adds WHERE company_id = ? to every query automatically from the resolved tenant context, and a matching Postgres Row-Level Security policy is the backstop so a bug in app code can never leak another company's rows. A user can belong to several companies with a different role in each.

05

Accounting engine — the spine

This is the schema everything else feeds. A journal is a voucher; its lines are the debits and credits. Two hard rules are enforced in the database, not just in code:

  • Each line has a non-negative debit or credit, never both (CHECK).
  • The sum of debits equals the sum of credits per journal, checked at transaction commit with a deferred constraint trigger — a journal literally cannot be saved out of balance.

Posted journals are immutable; corrections happen through reversing entries, so the audit trail is intact. Fast reports read from a maintained account_period_balances rollup rather than summing millions of lines.

Reports, straight off this schema

Trial Balance, General Ledger, Day Book, P&L, Balance Sheet, Cash Flow, and AR/AP Aging are all queries over journal_lines + account_period_balances, filtered by company, period, and optionally cost center. Single-entry / cash-book bookkeeping is offered as a simplified data-entry surface (a receipts & payments book) that writes the same balanced journals underneath — you get the easy UX without a second, inconsistent ledger.

06

The universal posting rule

Here is the mechanism that keeps the promise "every transaction in other modules posts to accounting automatically." Each source document implements one interface — toJournal() — returning a balanced set of lines. The Posting Engine wraps it in a transaction, validates the balance and the open period, writes the journal, and updates the balance rollup. Nothing else may write journals.

07

Inventory & valuation

The heart of inventory is one append-only table: stock_ledger_entries. Every receipt, issue, transfer, adjustment, and production move writes a signed quantity and a valuation rate, with a running quantity and running value per item-warehouse. Valuation method is configurable per item (company default applies otherwise):

Weighted average

Running value ÷ running qty

Cheap, smooth, no layer bookkeeping — recomputed on every inward move. Good default for manufacturing where raw materials are fungible.

FIFO

Consumes valuation layers oldest-first

valuation_layers holds each receipt's remaining qty & unit cost; an issue walks layers front-to-back. Exact cost of goods, batch-friendly.

Batch/lot tracking is standard; serial tracking is optional per item. Landed costs (freight, duty, clearing) allocate across receipt lines and raise the layer cost. Every stock move triggers a matching journal via the posting engine (e.g. issue to production: Dr WIP / Cr Raw-material inventory).

08

Manufacturing

A BOM lists component items (with scrap %) and, optionally, operations that carry labour and overhead. A work order issues raw materials into WIP, applies labour + overhead, and receives finished goods back at computed cost: FG unit cost = (material + labour + overhead − scrap recovery) ÷ good qty. Each step posts through the engine, so WIP on the balance sheet always equals real work in progress.

09

Purchase & sales

Both sides share a shape: a document flows order → receipt/delivery → invoice → payment/return, each step optional but linked. Purchase drives AP + inventory-in; sales drives AR + COGS + inventory-out. Taxes come from the configurable tax engine (§13), discounts and price lists resolve per line, and party ledgers are just the AR/AP subledger filtered by party_id.

10

Inter-warehouse consignment — the critical model

This is the piece worth getting exactly right. A consignment is a truck-load of goods that moves through an ordered chain of legs (stages), warehouse → warehouse → … → customer. Each leg records a buy value (cost of goods entering the leg), a sell value (transfer valuation leaving it, or the real customer sale on the last leg), and its own pile of expenses (transport, fuel, labour, loading, tolls, misc.). The margin of a leg is sell − buy − expenses; the carry-out of one leg is the buy of the next, so cumulative P&L telescopes to final sale − initial cost − all expenses.

11

HR & payroll

Employees sit in departments (each mapped to a cost center) with a salary structure of earning and deduction components. Attendance and leave feed a payroll run that produces payslips and posts one consolidated journal: Dr salary/wages expense per department cost center, Cr statutory-, deduction-, and net-pay payables. Paying salaries later clears the net-pay payable against the bank.

12

Build sequence

Bottom-up, so each module posts into something that already works. We build the spine first, prove inventory valuation next, then layer the flows that depend on both. Each phase ends with: schema/migrations → API → UI → wired into accounting → a passing test, and I pause for your review before the next.
